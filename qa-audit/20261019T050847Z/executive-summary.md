## Environment

Debian 13, kernel 5.10.134, 2 vCPU, 4 GiB RAM, root fs 9.9G (83–97% used
during the audit), rustc 1.99.1. GUI: Xvfb virtual display + llvmpipe
software Vulkan; input: python-xlib XTEST (the same X channel a physical
mouse/keyboard uses); capture: PIL/XCB PNG + ffmpeg x11grab MP4. No window
manager (bare Xvfb) — keyboard focus must be set explicitly; documented as an
environment characteristic, not a product defect. A sandbox janitor
terminated long-lived sessions at unpredictable ages (5–180 s), which the
audit worked around with short, self-contained scenario sessions; several
forensic sessions died mid-run and their partial evidence is preserved.

## Major findings (see `defects.md` for full evidence)

| ID | Severity | Finding |
|---|---|---|
| DEFECT-01 | MAJOR | Sidebar click hitboxes are compressed to the far-left ~15 px on exactly the four shortest labels (Inbox, Reports, Search, Shell). Clicks on the visible label text are ignored (hover highlight still paints — paint/hover rect decoupled from click rect). Users clicking those labels get no navigation and no feedback; the four pages appear unreachable by mouse. Workaround: click the row's far-left edge — verified working for all four. All rows are generated by one uniform `selectable_label(...).clicked()` loop (`app.rs` shell_ui); the strict ≤7-char correlation (1/5985 by chance) suggests an egui 0.37 hit-testing anomaly for short text, not app logic. |
| DEFECT-02 | MINOR | Palette Enter never confirms a hit: `response.lost_focus() && Enter` (`palette.rs:210`) is a web-port pattern; egui single-line TextEdit does not blur on Enter, so the keyboard path is dead as read. Mouse hit-click path unaffected. |
| DEFECT-03 | MINOR | Palette query input does not take keyboard focus when the palette opens (web counterpart auto-focuses); typed keys go nowhere until the user clicks inside the input. |

## Limitations

- GUI interaction depth was bounded by the sandbox janitor (documented
  per-scenario in `scenario-catalog.md`).
- No window manager in the environment: keyboard-focus behaviors that a WM
  would mediate (focus steal, alt-tab) were not testable; the app's own
  focus handling was verified via explicit `XSetInputFocus`.
- Performance numbers are meaningless in this environment (software GL,
  2 vCPU); prior recorded figures (release boot 10–11 ms, migrations
  914 ms cold / 4.1 ms warm, AppImage start 37–38 ms) live in the
  repository ledger (`ai/plan.md`, items 40–46) and were not re-measured.
- The final `git push` of this branch was blocked by the sandbox janitor
  removing the git credentials mid-audit (see `coverage-gaps.md` §6).
  Resolved post-audit: credentials were re-supplied, the branch was pushed,
  then merged fast-forward into `main` and deleted per maintainer
  instruction (single-branch policy).

## Verdict

**Ship-blocking defects: none.** One MAJOR navigation-usability defect
(DEFECT-01) should be fixed promptly — it makes four core pages look
unreachable to mouse users — and is fully characterized to make the fix
verifiable. The backend surface (data, sync, webhooks, OAuth, AI client,
workers) is exceptionally well covered by the repository's own
credential-free integration suite, which this audit re-verified green.

**Post-audit remediation (same day).** DEFECT-01 fixed and GUI-reverified
(`F1-fix-verify`: all four dead rows navigate at x=75 and x=130);
DEFECT-03 fixed (headless E2E proof of focus + keystroke delivery; the
on-screen leg is env-blocked after four janitor-killed attempts F2–F5);
DEFECT-02 invalidated — egui 0.37 surrenders TextEdit focus on Enter, the
Enter path works as written and is now covered by a headless E2E test.
See `defects.md` "Remediation" blocks and `fix-report.md`.
